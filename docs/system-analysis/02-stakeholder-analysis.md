# 02 — Stakeholder Analysis

## Stakeholders

### Household Admin
The member who created the household, or anyone since granted `role = 'admin'`
(`household_members.role`, set to `'admin'` on creation in
`householdController.createHousehold`).

- Creates the household and receives its invite code (`households.invite_code`,
  an 8-character code auto-generated by the schema).
- Updates household settings (`PUT /api/household/:id`).
- Removes a member (`DELETE /api/household/:householdId/members/:memberId`).
- Participates in every member-level workflow below like anyone else — the
  role only adds administrative actions, it doesn't gate day-to-day use.

### Household Member
Anyone who joined via `POST /api/household/join` with a valid invite code.

- Records expenses and loans, and settles their own share of either.
- Completes assigned chores; can also create/update/delete chores and
  assignments (chore management is not admin-gated in the current
  implementation — see [06-business-rules.md](06-business-rules.md) for why
  this is worth flagging as a scope decision, not an oversight).
- Proposes and votes on meals, joins/leaves a meal's attendee list.
- Manages shared inventory (add items, restock, adjust quantity).
- Can leave the household (`POST /api/household/leave`).

### The System (automated actor)
Not a person, but a stakeholder in the analysis sense: several rules run
without any user action, on the household's behalf, and their correctness
matters as much as any human-facing feature.

- Computes each member's net balance and simplifies the household's debt
  graph into the minimum settlements (`balanceService.ts`).
- Detects a chore assignment that passed its due date unfinished, resets
  that member's streak, and inserts a penalty re-assignment
  (`choreService.checkMissedChoreAssignments`).
- Expands a due recurring bill into a real expense + splits
  (`recurringBillService.generateDueRecurringBills`).
- Writes an audit trail of the above into `activity_log`
  (`activityService.logActivity`).

## Stakeholder matrix

| Stakeholder | Interest | Influence over the system | Key needs |
|---|---|---|---|
| Household Admin | High — accountable for the household's setup and membership | High — the only role that can remove a member or edit household settings | Control over membership; visibility into the whole household's activity |
| Household Member | High — the actual daily user of every feature | Medium — full read/write on their own data and shared household data, no elevated actions | Fairness (splits and rotations that are actually equal); minimal friction to record something |
| The System | — | — (it's not a person, but every other stakeholder depends on it being correct) | Deterministic, auditable calculations — the same inputs must always produce the same balances and streaks |

## Why this split matters for design

Two things fall directly out of this table and show up throughout
[04-requirements.md](04-requirements.md) and
[06-business-rules.md](06-business-rules.md):

1. Because **The System** is a stakeholder with its own "need" (determinism),
   money-math (`splitCalculator.ts`, `balanceService.ts`) is written to do
   all arithmetic in integer cents with an explicit, documented tie-breaking
   rule for leftover cents — "close enough" isn't acceptable for something
   users will audit against their own memory of who paid what.
2. Because **Household Member** has near-equal influence to **Admin** on
   purpose (fairness is the product's whole pitch), the authorization model
   is "any household member" for most write actions, with admin-only
   carved out narrowly (remove member, update household) rather than the
   other way around. A design that admin-gated chore/expense creation would
   contradict the stated goal of shared, equal accountability.
